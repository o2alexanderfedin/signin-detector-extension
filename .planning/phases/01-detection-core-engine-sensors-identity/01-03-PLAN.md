    **`fuseConfidence(vector: SignalVector): number`** -- weighted mean over observed-only signals (ENG-01), with one pre-processing cross-signal override (ENG-02):
    - Determine `hasPositiveCookie = vector.cookie?.observed === true && vector.cookie.value > 0`.
    - For each signal present in the vector with `observed: true`: its contributing value is normally `evidence.value`, EXCEPT for the `dom` signal specifically -- if `evidence.passwordFormVisible === true` AND `hasPositiveCookie === false`, its contributing value is overridden to `STRONG_NEGATIVE_VALUE` regardless of its own `value` (this is the ENG-02 password-form-with-no-session-cookie strong-negative rule; it must live here because the DOM classifier alone cannot know whether a cookie exists).
    - Sum `weight_i * contributingValue_i` over all observed signals (weight from `SIGNAL_WEIGHTS[signal]`), divide by the sum of `weight_i` for observed signals only. Unobserved signals contribute to neither the numerator nor the denominator.
    - If NO signals are observed at all, return `0` (avoids division by zero; a fully silent vector is not evidence of anything, and 0 is comfortably inside/below the SignedOut threshold).
    - Fixtures: `{}` -> `0`. `{cookie: {signal:'cookie', observed:true, value:1}}` (others absent) -> `1` (graceful degradation -- ROADMAP Phase 1 criterion 1's exact scenario). `{network: {signal:'network', observed:true, value:-1}}` (only signal) -> `-1` (ROADMAP criterion 2 -- decreases rather than neutral). `{dom: {signal:'dom', observed:true, value:0, passwordFormVisible:true}}` (no cookie) -> `-1` (cross-signal override fires, dom-only so result equals the override value exactly). `{cookie: {signal:'cookie', observed:true, value:1}, dom: {signal:'dom', observed:true, value:0, passwordFormVisible:true}}` (cookie IS positive) -> `1/1.3` (~0.7692; override does NOT fire because `hasPositiveCookie` is true -- assert with `toBeCloseTo(1/1.3, 5)`). One fixture combining all four signals with concrete numeric weights/values, with the expected weighted-mean hand-computed in the test comment so the assertion is self-documenting.

    **`nextVerdictState(confidence: number, previousState: VerdictState): VerdictState`** -- pure hysteresis, no time involved (ENG-03):
    - `confidence >= THRESHOLD_SIGNED_IN` -> `'signed-in'`.
    - `confidence <= THRESHOLD_SIGNED_OUT` -> `'signed-out'`.
    - Otherwise (hold band, `THRESHOLD_SIGNED_OUT < confidence < THRESHOLD_SIGNED_IN`) -> return `previousState` unchanged (no flicker).
    - Fixtures: `(0.5, 'unknown')` -> `'unknown'`. `(0.5, 'signed-in')` -> `'signed-in'`. `(0.5, 'signed-out')` -> `'signed-out'`. `(0.8, 'unknown')` -> `'signed-in'`. `(0.2, 'signed-in')` -> `'signed-out'`.   <name>Task 2: createConfidenceEngine -- stateful wrapper with injected clock and asymmetric debounce (ENG-04)</name>
  <files>src/engine/confidenceEngine.ts, src/engine/confidenceEngine.test.ts</files>

    **`createConfidenceEngine(clock: ClockFn = Date.now): ConfidenceEngine`** where `ConfidenceEngine = {update(vector: SignalVector): VerdictResult}`. Internal closure state: `committedState: VerdictState = 'unknown'`, `pendingSignedOutSince: number | null = null`.

    `update(vector)` algorithm (implement exactly this control flow -- it was verified during planning to correctly handle prompt entry, delayed exit, and cancellation-on-recovery in a single unified branch structure with no dead cases):
    1. `now = clock()`. `confidence = fuseConfidence(vector)`. `rawState = nextVerdictState(confidence, committedState)`.
    2. If `rawState === committedState`: clear `pendingSignedOutSince` to `null` (no transition in progress -- this also handles the case where a pending SignedOut countdown should be canceled because the raw hysteresis result is no longer `'signed-out'`, e.g. it fell back into the hold band). Return `{state: committedState, confidence}`.
    3. If `rawState === 'signed-in'`: commit immediately (`committedState = 'signed-in'`, clear `pendingSignedOutSince`). Return `{state: committedState, confidence}`. (Prompt entry -- `DEBOUNCE_SIGNED_IN_MS` exists as a named constant for symmetry/future tuning but no delay is applied in this phase.)
    4. Else `rawState === 'signed-out'`: if `pendingSignedOutSince === null`, set it to `now` (grace window starts). If `now - pendingSignedOutSince >= DEBOUNCE_SIGNED_OUT_MS`, commit (`committedState = 'signed-out'`, clear `pendingSignedOutSince`). Either way, return `{state: committedState, confidence}` (note: `committedState` here may still be the PRE-transition state if the grace window hasn't elapsed yet -- that is the whole point of the debounce).
    5. There is no fifth case: `nextVerdictState` can only return `'unknown'` when it already equals `previousState` (hold band echoes `previousState`, and `'unknown'` is never a threshold-crossing target), so `rawState === 'unknown'` is always caught by step 2.

    Fixtures (single engine instance per scenario, `clock` returning a mutable `t` you control from the test):
    - `t=0`: `update({cookie: {signal:'cookie', observed:true, value:1}})` -> state `'signed-in'` (prompt).
    - `t=1000`: `update({cookie: {signal:'cookie', observed:true, value:0}})` -> state still `'signed-in'` (pending timer just started at 1000, well within the 3000ms grace window).
    - `t=3999`: same low-confidence vector -> state still `'signed-in'` (2999ms elapsed, `< DEBOUNCE_SIGNED_OUT_MS`).
    - `t=4000`: same low-confidence vector -> state now `'signed-out'` (3000ms elapsed, `>= DEBOUNCE_SIGNED_OUT_MS`).
    - Fresh engine, recovery-cancels-pending scenario: `t=0` high-confidence -> `'signed-in'`. `t=1000` low-confidence -> still `'signed-in'` (pending starts at 1000). `t=2000` high-confidence again -> `'signed-in'` (recovery, pending is canceled per step 2/3). `t=5000` low-confidence -> assert state is still `'signed-in'` at this exact call (a NEW pending window has just started at `t=5000`; if the implementation incorrectly used the original `t=1000` pending timestamp, this call would incorrectly already read `'signed-out'` since `5000-1000=4000 >= 3000` -- this fixture specifically catches that bug).
    - Initial state before any `update()` call is `'unknown'` by construction (assert via a fresh engine's very first `update()` with a hold-band confidence vector returning `state: 'unknown'`).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Webpage-controlled data -> classify.ts pure functions | Untrusted page content (cookie names/values, storage keys/values, DOM affordance booleans, request URLs/statuses) flows into classifier inputs; a malicious page could try to shape this data to force a false "signed-in" verdict |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-02-01 | Spoofing | src/sensors/storage/classify.ts, src/sensors/dom/classify.ts | mitigate | Page-controlled localStorage/DOM data can never set an HttpOnly cookie attribute (browser-enforced), so the cookie classifier remains the anti-spoofing backbone; storage/DOM classifiers are deliberately kept at MEDIUM/LOW engine weight (`SIGNAL_WEIGHT_STORAGE=0.6`, `SIGNAL_WEIGHT_DOM=0.3` in Plan 01's constants.ts) specifically so a spoofed storage/DOM signal alone cannot cross the 0.7 SignedIn threshold without cookie corroboration |
| T-02-02 | Tampering | src/sensors/cookie/classify.ts entropy/expiry heuristic | mitigate | Classifier reads only structural shape (length, HttpOnly/Secure flags, expiry), never trusts cookie value content; a page cannot set HttpOnly cookies via `document.cookie`, so the strongest positive score requires a server-set attribute the page cannot forge |
| T-02-03 | Denial of Service | src/sensors/storage/classify.ts JWT-shape decode | mitigate | base64url decode of attacker-controlled localStorage values is wrapped in try/catch with a bounded segment-count check before any decode attempt; malformed input falls through to "not JWT-shaped" rather than throwing or hanging |
| T-02-04 | Information Disclosure | src/identity/appIdentity.ts | accept | tldts resolves only the hostname (already visible to any page via `location.hostname`); no new information is exposed beyond what the page itself can already read |
</threat_model>
